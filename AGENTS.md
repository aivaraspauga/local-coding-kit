# local-coding-kit: notes for contributors and agents

The kit an AI copies into a project (`SETUP-FOR-AI.md`), a launcher for the local model server and a benchmark. See README.md for what it does. The kit is for Qwen Code only (2026-10-27).

## Layout

- `1-copy-into-project/`: everything a project gets, and the only copy of the kit. `.qwen/settings.json` wires the hook scripts to Qwen Code events (`node .qwen/kit/scripts/<name>.mjs`: Qwen Code starts hooks in the project folder and runs Windows hooks through cmd, where quotes break), pre-approves routine commands, and turns off Qwen Code skills and tools that fight the kit. `QWEN.md` tells the AI that `.qwen/` is not part of its task. The setup only installs the kit: no starter app, no questions.
- `1-copy-into-project/.qwen/kit/scripts/`: the hook scripts (plain Node ESM, no dependencies). `readInput()` maps Qwen Code's tool ids to the short names the scripts use (`run_shell_command` -> `Bash`, `edit` -> `Edit`, ...). Shared helpers in `lib/project.mjs`: project root (true-case path), check-command detection, per-conversation state (keyed by `session_id`; helper agents send their parent's), fingerprinting. `lib/deps.mjs`: dependency release facts from deps.dev (cached a day, silent when offline), used by session start and `deps-check.mjs` (after installs). Tests point it at a stand-in server with `LOCAL_AGENT_DEPS_API`. `guard.mjs` treats `.qwen/kit` as its own guardrail; `reminder.mjs` records what only the user's message can say (an `allow <code>`, config files it names, a question).
- `1-copy-into-project/.qwen/kit/prompt/working-style.md`: the rules `session-start.mjs` injects. Keep it short; every line costs context on every session.
- `1-copy-into-project/.qwen/skills/<name>/SKILL.md`: skills. Concrete steps and copyable examples beat general advice. Name Qwen Code's tools (`read_file`, `grep_search`, `run_shell_command`, `edit`, `write_file`). `.qwen/agents/<name>.md`: helper agents (explorer, planner, tester, reviewer), each with `background: false`.
- `qwen-code/user-settings.json`: the Qwen Code user settings the kit is tuned for (local model provider, web search, no follow-up suggestions or background memory). `SETUP-FOR-AI.md` merges it with the user's OK; the benchmark uses it as its system settings.
- `SETUP-FOR-AI.md`: the steps an AI follows to install or update the kit from a temporary clone (`copy-kit.mjs` copies it, never overwrites a project file, and records what it added, with hashes, in `.qwen/kit/installed.json`), merge kept files, drop unused framework skills, then stop. Keep it in step with `1-copy-into-project/`.
- `1-copy-into-project/.qwen/kit/VERSION`: the kit's version, the date of the last change. Set it to today's date when you change anything in `1-copy-into-project/`. `.qwen/kit/REMOVE.md` with `scripts/remove.mjs`: the removal, from that record (`QWEN.md` points to it; the guard asks before `remove.mjs` runs).
- `launcher/`: `start-server.cmd` (starts llama-server with the target model and `qwen3.8-chat-template.jinja`), `start-all.cmd` (starts what is not running, then shows the status), `coding.cmd` (the "Coding Server" desktop shortcut: closes `LOCAL_AGENT_CLOSE_FOR_CODING` programs, then `start-all coding`), `start-extra.cmd` (git-ignored, machine-specific services that `start-all` calls when present), `status.mjs` / `status.cmd` (one line per service with what to do; tested in `tests/hooks.test.mjs`) and the config examples. `config.cmd` is machine-specific and git-ignored. `.cmd` files must keep CRLF line endings (`.gitattributes`).
- `backends/llama-cpp.md`: the one supported server and model, its flags and the first-start checklist.
- `docs/setup-guide.md`: the step-by-step setup (llama.cpp, model, SearXNG, VS Code). Keep its commands working when you change paths, flags or file names.
- `assistant/` (git-ignored: it stays on the author's PC, the repo is the coding kit only): the optional chat assistant (`docs/assistant-guide.md`, also git-ignored). `status.mjs` lists its services as OFF only when this folder exists. `docker-compose.yml` (Open WebUI + Word/PDF MCP tools on an internal network; carries the Qwen-Image 2.1 text-to-image workflow and its node mapping, applied on Open WebUI's first start only), `start-comfyui.cmd`, `comfyui/gate.mjs` (proxy in front of ComfyUI that waits while the language model is answering, then unloads it before each image job; refuses after `BUSY_WAIT_SECONDS`; frees ComfyUI's memory `FREE_AFTER_SECONDS` after its queue empties), `comfyui/nodes.mjs` (node IDs for Open WebUI, for your own workflows), `comfyui/llama_cpp_unload/` (the same unload as a ComfyUI node), `tools/word` and `tools/pdf` (MCP servers over HTTP). Tests: `node --test assistant/` and `python assistant/comfyui/test_llama_cpp_unload.py`.
- The model server runs in router mode, and every client must request the model by its preset name (`qwen3.8-27b`); `qwen-code/user-settings.json` and the benchmark (`--model`) use it.
- Only on the author's PC (git-ignored, not on GitHub): `benchmarks/`, `docs/findings.md`, `docs/decisions.md`, `docs/coverage.md`.
- `benchmarks/`: `run.mjs` (drives Qwen Code headless: the CLI bundled with the VS Code extension, YOLO, `stream-json`; model and server through a system settings file built from `qwen-code/user-settings.json`), `tasks/<fixture>.mjs`, `fixtures/<name>/` (source only), `lib/files.mjs`, `lib/fixture.mjs` (fresh fixture copies). `traps.mjs` with `traps/<fixture>.mjs`: checks the kit's version-specific advice against the fixtures' installed packages. Runners: `eslint`, `tsc` (a trap may bring its own `tsconfig.json` to test compiler defaults), `vitest`, `vuetsc`, `ngc` (one file at a time), `ngtest`, `node` (runs `.ts` files with Node's type stripping) and `nuxt` (requests pages from the dev server). Fixtures `next-starter` and `taskboard` also serve the benchmark tasks; `vue-starter`, `ng-starter`, `nuxt-starter`, `vanilla-starter`, `ng16-legacy`, `vue2-legacy` and `ts48-legacy` are only for traps; `vue-starter` and `ng-starter` have tasks too (an Angular task's hidden test runs through `ng test`).
- `tests/hooks.test.mjs`: tests for the hook scripts, the project files, `copy-kit.mjs` and `remove.mjs`. Hooks get Qwen Code's input (JSON on stdin, `QWEN_PROJECT_DIR`). The format-file tests need a project with ESLint and Prettier installed (`LCA_TEST_PROJECT`; a `prepareCopy("next-starter", dir)` from `benchmarks/lib/fixture.mjs` works).
- `docs/findings.md`: measured results. Update it when you measure something; record the setup and the number of runs.

## Commands

- `node --test tests/`: hook script, project-file and setup tests. Run after any change in `1-copy-into-project/`, `qwen-code/`, `SETUP-FOR-AI.md` or `launcher/`.
- `node benchmarks/run.mjs --self-test reference` (all must pass) and `--self-test noop` (all must fail): run after changing tasks or fixtures.
- `node benchmarks/traps.mjs` (`--offline` without the shadcn registry): run after updating a fixture's dependencies or changing version-specific advice. No model needed. `--fixture <name>` runs one app; all of them take several minutes (the first run installs each app's packages).

## Rules

- Hook scripts must never crash a session: read input defensively and exit 0 when a project lacks what a hook needs (no `package.json`, no ESLint, no Prettier).
- Hooks run on every tool call in every project. Keep them fast and dependency-free; use the project's own tools from its `node_modules`.
- Don't claim improvements in the README or findings without a measurement; say how many runs it was.
- When you change how the kit works, add or update its one line in `docs/decisions.md` (what and why).
- Version-specific advice (a session start fact, a "this API changed" line in a skill) needs a trap in `benchmarks/traps/` that proves it on a fixture. Reproduce a trap before writing advice about it.
- Don't put machine-specific paths or personal details in committed files.
- Write documents for people (`README.md`, `docs/` except `findings.md`, `backends/`, `benchmarks/README.md`) in plain, simple English: short sentences, everyday words, numbered steps for procedures. Say what to do and why, briefly. Keep commands, paths, numbers and heading anchors exact. Text for the model (`working-style.md`, skills, agents, `QWEN.md`), `findings.md` and code comments keep their own style.
